# Object-oriented design

## Inspect first

0. `docs/requirements.md` - which seams the specification actually requires, and the
   design decisions still open. The store must be extensible **and selectable
   through configuration**; that requirement is why `IOrderAggregator` exists and is
   not a candidate for removal under YAGNI.
1. `src/OrderAggregationService/Services/IOrderAggregator.cs` - the seam the whole
   API layer depends on, and the model for a justified abstraction
2. `src/OrderAggregationService/Services/OrderAggregationServiceCollectionExtensions.cs` -
   how implementations are bound
3. The type you are about to change, and every caller of it
4. `README.md`, the architecture section - the intended direction

## Decision procedure

Before adding any type, interface or pattern, answer these in order. If you cannot
answer 1 concretely, stop.

1. **What specific problem does this solve?** Name the failure or friction that
   exists today.
2. **Does the change actually solve it?** If it only relocates the problem, it is
   not a fix.
3. **What is the simplest thing that solves it?** Start there.
4. **Is the result less complex than before?** Count types, indirections and the
   number of files a reader must open. If any went up without a reason from step 1,
   revert.

## Principles as applied here

**Encapsulation.** State is private; invariants are enforced where the state lives.
`InMemoryOrderAggregator` owns its lock and its dictionary and never hands either
out. Do not add a property that lets a caller mutate internal state.

**Cohesion.** A type does one job. If you cannot describe it in one sentence
without "and", split it.

**Coupling.** Depend on the narrowest thing that works. The endpoints depend on
`IOrderAggregator`, not on the in-memory implementation, which is exactly why the
store can be replaced without touching the API.

**Composition over inheritance.** Inherit only from a framework base class that is
designed for it, such as `BackgroundService`. For sharing behaviour between your
own types, compose or use an extension method.

**Dependency inversion.** High-level policy defines the interface; the low-level
detail implements it. `IOrderDispatcher` is defined by the dispatch cycle's needs,
not by whatever a future HTTP client happens to offer.

**Fail fast.** Validate at the boundary and construct only valid objects.
`OrderLine` throws on an empty product id or a non-positive quantity, so nothing
downstream has to re-check.

**Immutability.** Prefer `sealed record` for data that crosses a boundary.
Everything in `Models/` is immutable; keep it that way.

**Tell, don't ask.** Push behaviour to the data. `ProductAccumulator.Add(...)`
rather than reading its counters, adding outside, and writing them back.

**Principle of least astonishment.** A method named `DrainAsync` removes what it
returns. Do not give a familiar name surprising behaviour.

## SOLID, DRY, KISS, YAGNI - and their misreadings

- **SOLID** is not a licence to create an interface per class. Create an interface
  when there is a second implementation, a genuine test seam, or a published
  contract. `IOrderAggregator` qualifies: it is the persistence seam. A
  single-implementation interface with no test or substitution value does not.
- **DRY** targets duplicated *knowledge*, not duplicated *shape*. Two validators
  that look alike but change for different reasons must stay separate. Merging
  them creates a type with two masters.
- **KISS** never outranks correctness. Removing a lock, a cancellation check or a
  null guard to "simplify" is a defect.
- **YAGNI** does not delete extensibility the task explicitly asked for.
  `IOrderDispatcher` exists because the brief calls for a future dispatch
  integration. Do not remove a seam the requirements named.
- **Separation of concerns** means the HTTP shape, the aggregation rules and the
  dispatch schedule change for different reasons and live in different files.

## Patterns, and when they earn their place

| Pattern | Use it when | Already here |
| --- | --- | --- |
| Store / repository abstraction | Persistence must be swappable | `IOrderAggregator` |
| Strategy | Two or more interchangeable algorithms are selected at runtime | `IOrderDispatcher` |
| Background worker | Work runs on a schedule independent of a request | `OrderDispatchBackgroundService` |
| Options | Configuration is bound and validated at startup | `OrderAggregationOptions` |
| Result | A failure is expected and callers must branch on it | `OrderBatchValidationResult` |
| Decorator | Cross-cutting behaviour wraps an existing contract unchanged | retry or logging around `IOrderDispatcher` |
| Adapter | An external shape must be translated to a domain shape | when a real downstream API arrives |
| Factory | Construction genuinely varies, beyond calling a constructor | not yet |
| Null object | A no-op implementation removes null checks at many call sites | not yet |
| Retry / circuit breaker | A remote call fails transiently | when dispatch talks to a real system |
| Outbox | A drain and a send must not lose data across a crash | listed as a future improvement |

Use the pattern name in a comment or a type name only when the implementation
really is that pattern.

## Antipatterns to refuse

- An interface with exactly one implementation, no test seam and no plan for a
  second
- Layers or projects added to satisfy a diagram rather than a requirement
- Service locator: injecting `IServiceProvider` and resolving inside business code
- God object: a type that grows a new responsibility every time the feature does
- Anemic model: data-only types plus a `...Service` holding all the behaviour,
  where the behaviour clearly belongs on the data
- Premature generalisation: a type parameter, hook or configuration switch with one
  caller
- Inheritance used to share a helper method
- Static mutable state
- An abstraction whose only implementation is a test double

## Verify after a design change

- The number of types, files and indirections went down, or the increase is
  justified by the problem from step 1
- Every new interface has a named second implementation, a test seam, or a
  requirement behind it
- Public behaviour is unchanged unless the task asked to change it
- Existing tests still pass without being rewritten to match the new shape; a test
  that had to change usually means observable behaviour changed
- `dotnet build --configuration Release` is warning-free and `dotnet test` passes
